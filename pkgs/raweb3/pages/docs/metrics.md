`--metrics 127.0.0.1:9669` serves `/metrics` in the Prometheus text format on
its own listener, separate from `--pprof` so a fleet node can be scraped without
exposing a profiler. The flag is empty by default, which serves no listener.
`ranet3 metrics` prints the same scrape over the
[control socket](control-socket.md), with or without the listener.

It reports neighbor liveness and link cost, routes received per neighbor, routes
selected and originated, established sessions per path, packets each peer chose
not to send, inbound ESP packet and drop counters, and the
[sockets connected to 1 peer](platforms.md#sockets-connected-to-1-peer) with
those that failed and handed their peer back to the shared socket and the
connects that failed.

It also reports 3 subsystems that run inside the daemon. The route reconciler is
reported as routes installed and skipped, when its last pass finished, whether
that pass failed, the overlay prefixes another program takes, on Linux the
endpoints its rule takes too and, under `cap.exit.fallback = "none"`, whether
the [kill switch](routing.md#the-kill-switch-on-linux), or on macOS
[its rejects](routing.md#the-kill-switch-on-macos), held, on Linux with the
packets it dropped. Segment routing is reported as what this node did for peers
(forwarded, delivered, dropped, answered, refused, the packets an `End.DT46`
took out of an unused ECN combination, and for an egress segment egressed and
not ready) and what it did with its own traffic (steered, and dropped with a
reason). `cap.egress` is reported as rules installed, connections translated and
connections a class of `none` left untranslated, packets refused past their
source's share and packets dropped with no tracked flow in each family, the
host's connection table against its maximum, other translation found at the same
hook, when its last pass finished and whether that pass failed, whether each
family is [ready](exit-nodes.md#readiness), and the 2 prefix counts whose
difference says this node is withholding an advertisement it cannot stand
behind. The refused and dropped counts are read from the limit chain's rules at
each pass, so they lag by up to 1 pass, and a rewrite of the chains starts them
from 0, which a scrape reads as a counter reset. A pass that cannot read them
back keeps the last pass's, unless it rewrote the chains, whose counts start
from 0 whether or not it read them back.

[The antispoof filter](antispoof.md) is reported as whether its table reads
back, both chains and every set, and the packets each of its drops counted, by
`reason` and `family`: `overlay_source` and `carved_source` from chain
`antispoof`, and `mesh_entry`, what the entry chain kept out of the tun. A drop
has a series in each family a rule of the last pass drops it in, and none
otherwise, as [watching it](antispoof.md#watching-it) lists. The counts are read
from the table at each pass, so they lag by up to 1 pass, and a rewrite of the
table starts them from 0, which a scrape reads as a counter reset. On macOS,
where `overlay` is written, the same series read the pf anchor
`com.apple/ranet3`, whose readiness takes pf's reference, the main ruleset's
call and no interface outside the mesh that pf skips too, as
[readiness](antispoof.md#readiness) gives, and `mesh_entry` has no series, since
the anchor holds no entry chain.

A node without `cap.table` writes none of the reconciler's series, a node
without `cap.egress` writes none of the egress series, and a node that runs no
antispoof filter, off Linux and macOS or on a Mac with no `overlay`, writes none
of the antispoof filter's. Zeros there would read as a subsystem installing
nothing. Segment routing writes its series on every node, zeros included.

The reconciler's, the egress and the antispoof filter's series hold their last
pass as it read them, as the paragraphs above say. Every other series is read
from live state at scrape time. The `forwarded`, `delivered` and `dropped`
counts of `ranet3_transit_packets_total`, `ranet3_steered_total` and
`ranet3_steer_dropped_total{reason="no_route"}` take each read off the tun and
each batch a session delivered once it is decided, so a scrape leaves out the
ones being decided as it runs. A counter cannot carry the route table.
`ranet3 routes` reads it, with each prefix's next hop, from the control socket.

## Transit counters

`ranet3_transit_packets_total` counts what the
[forwarding decision](routing.md#transit) did with each packet a session
delivered that no segment of this node took, and with each inner packet an
`End.DT46` delivering to the mesh handed it. It also counts each read off the
tun that this node dropped: for not being exactly one IP packet, for a multicast
destination or the limited broadcast, at the mesh's edge, where it checks what
the tun hands this node before the packet enters the mesh, for no route or a
hold, or for its size. `decision` is `forwarded`, `delivered`, `dropped`,
`answered`, `unanswered` or `unsent`, and `reason` names why a packet was
dropped and is empty for every other decision. The dropped series sum to the
packets and reads dropped. A read this node hands its peer's send, whole or cut
into fragments, counts under no decision, and `ranet3_peer_send_dropped_total`
counts one that peer's budget refuses.

| `dropped`    | `sid`             | reads off the tun addressed to one of this node's own SIDs                                                                                                                                                                                                                                                                                                                     |
| `dropped`    | `unowned_source`  | reads off the tun from a source this node does not own toward an entry that counts as a default, or under `cap.exit.via` toward a destination outside the overlay that no entry covers, and on every platform but Linux, where no entry chain runs, toward any destination but an IPv6 link-local one                                                                          |
| `dropped`    | `nested`          | reads off the tun whose inner packet, opened one level deep, carries another IP packet inside                                                                                                                                                                                                                                                                                  |
| `dropped`    | `looped`          | reads off the tun the table answers as this node's own whose destination the tun does not hold, which the mesh could only hand back to the host                                                                                                                                                                                                                                |
| `answered`   |                   | ICMP errors sent about dropped packets and reads                                                                                                                                                                                                                                                                                                                               |
| `unanswered` |                   | dropped packets the decision would answer that find no address of their family to come from                                                                                                                                                                                                                                                                                    |
| `unsent`     |                   | answers due about dropped packets where no way back carries the answer: to a source only an entry of this node counting as a default reaches, back through a peer no route takes or whose session's budget has no room, or beyond the scope of a link-local source of no session                                                                                               |

`unanswered` counts a drop before the rules that keep an error from answering a
packet, such as one about an ICMP error or to a group, and before the rate
limits, so it counts a drop that would have drawn no answer with an address too.
A drop whose answer is due and has no way back counts under its reason and
`unsent`. An answer to a source only this node's own default reaches, or beyond
the scope of a link-local source of no session, is found due without drawing on
a rate limit and is never built, and one back through a peer is built and then
not sent. A drop no ICMP error may answer, such as one of an ICMP error, counts
under no `unsent`, whatever way back its source has. An ICMP error a rate limit
held back counts in none of `answered`, `unanswered` and `unsent`, and
`ranet3_icmp_withheld_total` counts it, as [path MTU](#path-mtu) says. Every
series is written from startup, at 0 on a node that forwarded nothing.
`ranet3 status` shows the same counts on its `Transit` line.

## Tun reads

`ranet3_tun_reads_truncated_total` counts reads off the tun that lost the tail
of a GSO frame, because the frame split into more packets than 1 read holds.
Only Linux hands the tun GSO frames, so the counter stays at 0 elsewhere. There
ranet3 sets the device's `gso_max_segs` to that read batch, 128 packets,
whenever it creates the device or attaches to one, which has the kernel split a
larger frame before it reaches the tun and keeps the counter at 0. A kernel that
refuses the setting leaves a warning in the log at startup, and a sender with a
small MSS then cuts reads short. Each such read loses the rest of its frame,
which TCP sends again, and the reader goes on. A warning carries their count
since the previous warning, at most once every 30 seconds.

`ranet3_tun_frames_refused_total` counts frames the tun handed over that could
not be read as packets, and each such frame is lost alone while the reader goes
on. On Linux that is a frame whose virtio-net header does not describe its
packet, which a sender that writes the header itself, as through an `AF_PACKET`
socket, can produce, or one the kernel could not copy out. A warning and a
`netstack.tun.refused` event carry their count since the previous warning, at
most once every 30 seconds. Any other error reading the tun means the device is
gone, and the node then stops as
[the service](service.md#restarts-and-the-network) describes.

`ranet3_tun_writes_failed_total` counts writes to the tun that returned an
error, each of up to 128 packets, some or all of which the device did not take.
A `netstack tun refused a write` warning carries the interface, the queue, the
writes refused since the previous warning and the error of the write that raised
it, at most once every 30 seconds, and none once the mesh is closing or the tun
is gone.

## Refused datagrams

`ranet3_receive_refused_total` counts each inbound datagram nothing on this node
wanted under the `cause` of the check that refused it. Every cause is written
from startup, at 0 on a node that refused nothing for it, and their sum is the
`datagrams refused` of the `ESP` line of `ranet3 status`.

| `cause`          | Counts                                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `short`          | datagrams shorter than the 4 octets of an SPI, but for a NAT keepalive, which `ranet3_receive_keepalives_total` counts                   |
| `short_ike`      | IKE datagrams too short behind their non-ESP marker to name the initiator's SPI                                                          |
| `unknown_ike`    | IKE datagrams of an SA no session holds, on a node that does not listen or with no address to answer them at                             |
| `unknown_esp`    | ESP datagrams of an SPI no session holds                                                                                                 |
| `unclaimed_full` | IKE datagrams of an SA no session holds, for a listening node's queue of them that is full                                               |
| `truncated`      | datagrams the kernel cut, or whose control message it cut, and on Linux datagrams of 0 octets, each datagram of a coalesced read counted |
| `control`        | datagrams whose control message would not parse, a coalesced read counting once                                                          |
| `endpoint`       | IKE datagrams whose source, or the address they reached, would not read into an address to answer them at                                |

## Packets a peer did not send

`ranet3_peer_send_dropped_total` counts, per peer, every packet this node chose
not to send. A peer holds packets from the read that brought them to the
transmit that carries them within a budget of its own, which
[the design's limits](design/limits.md) give. A read that does not fit is
dropped whole rather than waited for, so a peer whose transport falls behind
never holds up another. Each budget refuses whatever it has no room for: reads
off the tun, the forwarding decision's forwards, the segments an End sent on,
the ICMP errors this node built, path MTU probes, and Babel's packets, which a
control budget of their own holds. The counter also takes the packets of a peer
that was closing, of reservations its outbound SA refused and of batches that
failed to seal, and the packets the delay control drops.
`ranet3_peer_send_delay_dropped_total` is that last part on its own. Each peer's
sender measures how long every data batch has waited since it was reserved, and
once that delay has stayed above 5 milliseconds for 100 milliseconds it drops 1
packet at the head of the queue on the schedule CoDel (RFC 8289) sets, until a
batch comes through below 5 milliseconds again or the queue empties. Babel's own
packets wait in the same queue, but the delay control neither measures nor drops
them. The sender records each start and end of that state as an event,
`netstack.codel.dropping` and `netstack.codel.drained`, which
[the debug tree](development/debug.md) shows.

Delay drops say the queue toward that peer stands. This node cannot seal and
send for that peer as fast as traffic for it arrives, because its CPU, its
socket or the path falls behind. TCP senders are told to slow down, as a
router's queue would tell them. The delay runs from the reservation, which makes
it count the seal and the wait for the encryption workers every peer shares. On
a node whose CPU is saturated, delay drops tend to show on every busy peer
together, and they mean this node cannot seal and send as fast as traffic is
offered, not that a path is slow. The rest of the counter, the total less the
delay drops, counts what the budgets refused, together with a closing peer's
packets, reservations the outbound SA refused and batches that failed to seal.
The last 2, and a batch sealed for a peer that closed before taking it, leave a
`netstack send batch failed` warning in the log naming `dropped_total`, this
counter, but for the segments an End sent on and the ICMP errors sent through a
peer, whose loss to a closed peer leaves the warning
`the transport lost a forwarded segment` or `the transport lost an icmp error`
instead, at most once every 30 seconds with the other segment drops. A closing
peer ends its session, so the rest climbing on a live session without that
warning is a budget refusing: a burst, a CPU that cannot keep the peer's sender
running, or a transport that stopped taking packets for longer than the budget
lasts. `ranet3_peer_send_failed_total` stays apart from all of these: those
packets were sealed and the transport lost them, which is the link failing
rather than this node choosing, and their warning names `send_failed_total`. A
peer writes 1 of the 2 warnings at most once every 10 seconds.

## Path MTU

`ranet3_packet_too_big_sent_total` counts the answers this node sent to packets
larger than their session carries, Packet Too Big over IPv6 and fragmentation
needed over IPv4 with DF, read off the tun or carried to a waypoint, and
`ranet3_mss_clamped_total` each time it lowered the MSS of a TCP SYN or SYN-ACK
to what a session carries, twice for a forwarded one it lowered to the session
it arrived on and again to its next. Both count for the node as a whole.
`ranet3_pmtu_probes_total` counts the probes of the sessions' path MTU that
left, by `result`: `acked`, or `lost` when no Ack came within the time a probe
waits, and [debugging](development/debug.md) says which probes count in neither.
Lost probes climbing on a node whose sessions have settled say a path loses its
session's largest packets now and then, and
[`ranet3 debug pmtu`](development/debug.md) names the session and shows its
search. [Path MTU](path-mtu.md) describes the search itself.

`ranet3_icmp_withheld_total` counts the ICMP errors the
[rate limits](path-mtu.md#packets-that-do-not-fit) held back, as the kernel's
`IcmpOutRateLimitHost` and `IcmpOutRateLimitGlobal` do. `limit="source"` rising
alone is a sender drawing past its own bucket, such as a flood of expired
probes, and costs no other sender anything. `limit="node"` rising is answers
past the node's cap, from many sources at once, and the cap then holds back
every sender's answers but Packet Too Big and fragmentation needed, which
neither limit holds back.

## Babel fragments

`ranet3_babel_reassembled_total` counts, per neighbor, the Babel packets its
session sent in fragments that this node put back together and read, and
`ranet3_babel_reassembled_largest_bytes` is the largest of them, a whole IPv6
packet with its headers. `ranet3_babel_reassembly_dropped_total` counts the
datagrams dropped instead, by `reason`:

| Reason      | Meaning                                                                                                                                                                           |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `overlap`   | A fragment overlapped another.                                                                                                                                                    |
| `header`    | A first fragment lacked the UDP header.                                                                                                                                           |
| `malformed` | A fragment was wrong in itself, or the speaker refused the whole packet.                                                                                                          |
| `timeout`   | A datagram was still incomplete 16 seconds after its first fragment.                                                                                                              |
| `evicted`   | A datagram at least 1 second old gave its place or its storage to another datagram of the same neighbor.                                                                          |
| `refused`   | A datagram found no storage, or a fragment found no place, while the neighbor's other datagrams, all younger than 1 second, held them. Each fragment refused a place counts once. |

A neighbor flooding fragments of datagrams that never complete has the node hold
under 280 KiB and allocate under 2 MiB a second. The node evicts and refuses
only that neighbor's datagrams. A neighbor that sent no fragment has none of the
3 series, so the series name exactly the neighbors whose stacks cut their
packets. [The protocol deviations](design/protocol-deviations.md) say which
fragments the speaker takes and the bounds it holds each neighbor to. The first
packet a session sent in fragments is recorded as a `babel.neighbor.fragmented`
event as well, which [the debug tree](development/debug.md) shows.
